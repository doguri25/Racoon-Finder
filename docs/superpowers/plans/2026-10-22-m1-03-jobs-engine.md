# M1-03 rf-jobs 파일 작업 엔진 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 복사·이동·삭제·이름 바꾸기·새로 만들기·되돌리기를 백그라운드 작업(Job)으로 실행하는 `rf-jobs` 크레이트를 만든다. 대기열과 진행률, 충돌 처리, `.rfpart` 원자적 쓰기, 오류 목록과 재시도, 메타데이터 보존, 사전 검사, 완료 보고, 되돌리기 기록, 작업 저널과 충돌 후 복구를 포함하고, 이에 필요한 메타데이터·링크 기능을 `rf-platform`과 `rf-vfs::Provider`에 더한다.

**Architecture:** `rf-jobs`는 UI와 무관한 블로킹 라이브러리다. 작업 하나는 `execute(id, spec, env)`가 현재 스레드에서 끝까지 실행하고(계획 → 사전 검사 → 실행 → 보고), `JobEngine`은 이를 `std::thread` 워커, `Mutex`+`Condvar` 대기열, `mpsc` 이벤트 채널로 감싸서 어떤 메서드도 호출 스레드를 I/O로 막지 않는다(REL-03). 동시성 단위는 레인(lane)이다. `LanePolicy`가 작업마다 레인을 고르고, 레인마다 워커 스레드 하나가 대기열 순서대로 하나씩 실행한다. M1의 `DefaultLanes`는 전송·삭제를 `MAIN` 하나에서 순차로(XFER-01), 이름 바꾸기·새로 만들기를 `QUICK`에서 돌리므로 긴 복사 뒤에 이름 바꾸기가 기다리지 않는다. M2의 XFER-02는 물리 디스크마다 레인을 주는 정책 하나를 더하면 되고 호출자 API는 바뀌지 않는다. 비동기 런타임(tokio)은 쓰지 않는다. `Provider`가 블로킹 API이고(M1-02), 동시 작업 수가 적어 스레드 몇 개면 충분하며, PRD 원칙 2(가볍게)와 PERF-05 메모리 예산에 맞기 때문이다. 모든 파일 접근이 `rf_vfs::Provider`를 거치므로, 결함 주입 공급자(`testkit::FaultyProvider`)로 쓰기 실패·디스크 가득 참·fsync 실패·파일 중간 강제 종료·다른 볼륨 이동을 Linux 컨테이너에서도 재현한다(REL-01, PRD 9). 저널은 `AppPaths::data_dir()/jobs.journal` JSON 줄 파일이고 전용 스레드 하나가 쓴다(REL-02).

**Tech Stack:** Rust stable(edition 2024, MSRV 1.85), rf-core·rf-platform·rf-vfs(M1-01·M1-02), std 스레드·`mpsc`·`Mutex`/`Condvar`, serde(derive)·serde_json(저널), unicode-normalization(APFS 이름 충돌 검사), rustix xattr·libc `lchflags`(macOS)·windows `FindFirstStreamW`/`SetFileAttributesW`(rf-platform 안), tempfile·proptest(개발 의존성).

**Spec:** docs/PRD.md (앞선 계획: `docs/superpowers/plans/2026-10-22-m1-01-workspace-core.md`, `docs/superpowers/plans/2026-10-22-m1-02-vfs-local.md`)

## Global Constraints

- M1-01과 M1-02 계획의 Global Constraints를 모두 따른다: edition 2024, `rust-version = "1.85"`, `GPL-3.0-or-later`, 새 크레이트 매니페스트 상속 블록과 `[lints] workspace = true`, 의존성은 `cargo add`로만(버전 숫자를 손으로 쓰지 않음), `Cargo.lock` 커밋, 제품 이름은 `rf_core::identity`에만(문서 주석에서도 "the app"), `cfg` 규칙, 표준 검사(`cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`)와 교차 검사(호스트가 아닌 두 타깃의 같은 clippy), 영어 conventional commits, 커밋 전 `cargo fmt --all`, MSRV 1.85 밖 API 금지(`io::ErrorKind::{CrossesDevices, StorageFull, DirectoryNotEmpty}`와 `File::set_times`, `FileTimesExt::set_created`는 1.85 안이다).
- 새 크레이트는 `crates/rf-jobs` 하나다. `unsafe`는 한 줄도 없다. FFI는 `rf-platform`에만 둔다(M1-02 규칙). 루트 파일, `deny.toml`, CI 파일은 고치지 않는다.
- 데이터 무결성 규칙(REL-01, XFER-07, DND-06, OPS-03). 테스트가 이 규칙을 직접 검사한다.
  1. 파일·링크 내용은 대상과 같은 폴더의 임시 이름 `.rf-{job:016x}-{seq}.rfpart`에 쓰고, `WriteStream::finish`(fsync) 뒤 `Provider::rename` 한 번으로 최종 이름에 커밋한다. 최종 이름에 일부만 쓴 파일이 생기는 경로는 없다. 실패·취소·패닉이면 임시 파일을 지운다.
  2. 이동의 원본은 그 항목의 커밋이 성공한 뒤에만 지운다. 원본 폴더는 `Provider::remove_dir`(빈 폴더만)로만 지운다. `delete(Permanent)`로 원본 폴더 트리를 지우지 않는다.
  3. 휴지통 삭제가 안 되면 실패로 보고하고 영구 삭제로 바꾸지 않는다. 덮어쓰기는 `RenameMode::Replace` 커밋으로만 하므로 실패하면 기존 내용이 그대로 남는다.
  4. 파일과 폴더는 서로를 덮어쓰지 않는다(어떤 충돌 정책이어도).
- REL-03: `JobEngine`의 모든 공개 메서드는 메모리 잠금과 채널 전송만 하고, 파일 I/O를 하거나 워커를 기다리지 않는다(`shutdown`만 예외이며 앱 종료 때 UI가 닫힌 뒤 부른다). `LanePolicy::lane`도 블로킹 I/O를 하지 않는다. `execute`는 블로킹이며 엔진 워커와 테스트·명령줄 도구에서만 부른다.
- rf-jobs 제품 코드는 파일을 `Provider`로만 다룬다. `std::fs`는 저널(`src/journal.rs`)과 `testkit`, 테스트에서만 쓴다.
- `Provider`·`WriteStream`에 더하는 메서드는 모두 기본 구현이 있는 메서드다(다른 공급자 구현이 깨지지 않게). `testkit::FaultyProvider`는 새 메서드까지 모든 메서드를 안쪽 공급자에 위임한다(빠뜨리면 기본 구현이 불려 `LocalProvider` 동작이 사라진다).
- `rf_core::Error::io`의 `op` 이름에 더한다: rf-platform `"set_times"`, `"set_attributes"`, `"copy_extras"`, `"data_ranges"`, rf-vfs `"read_link"`, `"create_symlink"`, `"remove_dir"`, `"write_hole"`, rf-jobs `"read"`, `"write"`, `"journal"`.
- 고정 값: `COPY_CHUNK` = 1 MiB(`1 << 20`), `PROGRESS_INTERVAL` = 100 ms, `SPEED_WINDOW` = 3 s, `MTIME_TOLERANCE` = 2 s(FAT32 시각 해상도), `MAX_DEPTH` = 128(macOS 1,023바이트 경로 한도 안에서 링크 고리를 끊는 깊이), `UNDO_LIMIT` = 100, `MAX_NUMBERED` = 9,999, `FAT32_MAX_FILE` = 4,294,967,295, `NAME_LIMIT` = 255, 경로 한도 Windows 32,000 UTF-16 단위·macOS 1,023 바이트·그 밖 4,095 바이트.
- 스레드 이름: 레인 워커 `rf-jobs-lane-{n}`, 저널 `rf-jobs-journal`.
- `Display`·로그 문자열은 이 계획에 적힌 영어 그대로다. 사용자 문구는 UI가 `Stage`, `ErrorKind`, `IssueKind`로 골라 번역한다(I18N-02).
- 실제 휴지통을 쓰는 테스트는 `rf_core::identity::TEMP_PREFIX`로 시작하는 고유 이름을 쓰고 끝나면 휴지통에서 지운다(M1-02 규칙).
- "실패를 확인한다" 단계의 컴파일 오류 문구는 예시다. 아직 없는 항목을 가리키는 `E0425`·`E0432`·`E0433`·`E0599`·`E0583` 중 무엇이 먼저 나와도 되고, 테스트가 컴파일되지 않아 `test result` 줄이 없으면 실패가 확인된 것이다.
- `crates/rf-jobs/tests/*.rs`의 모든 테스트 파일은 첫 줄에 `#![allow(clippy::many_single_char_names, reason = "short fixture names in tests")]`를 둔다(코드 블록에서는 생략했다. `f`·`p`·`e`·`a`·`b` 같은 픽스처 이름이 pedantic 한도 4개를 넘는다). 제품 코드와 `testkit`은 표준 출력·오류에 쓰지 않는다(`print_stdout`·`print_stderr` 린트).
- 테스트 수는 Linux 기준이고 OS마다 다르면 괄호에 적는다. Linux 컨테이너에서는 `cfg(windows)`·`cfg(target_os = "macos")` 테스트가 0개로 컴파일되며, 그 실행은 Task 19의 CI와 Task 20·21의 실기가 맡는다. 거의 모든 태스크에 `cfg` 코드나 OS별 테스트가 있으므로 표준 검사 뒤에 교차 검사를 늘 돌린다.

## Review Focus

- 파일을 같은 폴더에 붙여 넣거나(복사) 원래 폴더에 다시 놓는(이동) 경우 → 복사는 정책과 상관없이 `파일 (2).txt`를 만들고 원본을 절대 덮어쓰거나 비우지 않으며, 이동은 아무것도 하지 않는다(DND-09, DND-11). (Task 9 `copy_onto_itself_makes_a_numbered_copy`, Task 11 `moving_onto_itself_does_nothing`)
- NTFS와 FAT32·exFAT USB 사이에서 "더 새 파일만 덮어쓰기"를 반복하는 경우 → FAT의 2초 시각 해상도 때문에 같은 파일을 매번 다시 복사하지 않는다. (Task 7 `newer_uses_a_two_second_tolerance`, Task 9 `if_newer_ignores_two_second_clock_noise`)
- 다른 볼륨으로 폴더를 옮기다 일부 파일이 실패하거나 건너뛴 경우 → 실패한 파일은 원본 자리에 그대로 있고, 각 파일은 정확히 한 곳에만 온전한 내용으로 있으며, 원본 폴더는 남는다. (Task 11 `a_partial_cross_volume_move_keeps_what_failed`, Task 13 `random_faults_never_lose_data`)
- 이동하는 동안 다른 앱이 원본 폴더에 새 파일을 만드는 경우 → 복사되지 않은 그 파일은 지워지지 않는다(원본 폴더는 빈 폴더일 때만 지운다). (Task 11 `a_file_created_during_the_move_is_not_lost`)
- 복사를 되돌리기 전에 사용자가 복사본 하나를 고친 경우 → 고친 파일은 그대로 두고 손대지 않은 복사본만 휴지통으로 보낸다. 휴지통이 없으면 아무것도 지우지 않는다. (Task 16 `undo_of_a_copy_trashes_copies_but_keeps_edited_ones`, `undo_of_a_copy_without_trash_deletes_nothing`)

## 이 계획이 일부러 다루지 않는 PRD 항목

- XFER-02 장치 인식 스케줄링(M2): `LanePolicy` 구현 하나로 더한다. 이 계획은 레인 구조와 `a_lane_policy_can_run_jobs_in_parallel` 테스트로 API가 준비됐음을 보인다.
- XFER-03 이중 버퍼·캐시 우회 I/O, XFER-04 작은 파일 병렬 워커, XFER-05의 clonefile·블록 복제·SMB 오프로드(M2): 이 계획은 1 MiB 단일 버퍼로 복사한다. 같은 볼륨 이동 = 이름 바꾸기는 이동의 기본 의미라서 여기서 구현한다. PERF-07·08·09 목표 측정도 M2다.
- XFER-08 해시 검증과 DND-06의 "검증까지 성공 후 원본 삭제"(M2): 원본 삭제 지점이 커밋 직후 한 곳이라 검증 단계를 그 앞에 끼우면 된다.

/// Providers that need OS privileges for links (Windows without Developer Mode) pass by
/// refusing the first link.
pub fn check_links(p: &dyn Provider, root: &VPath) {
    let d = fresh(p, root, "links");
    let file = d.join("f.txt").unwrap();
    write_all(p, &file, WriteMode::CreateNew, b"target");
    p.create_dir(&d.join("sub").unwrap()).unwrap();
    let (flink, dlink) = (d.join("flink").unwrap(), d.join("dlink").unwrap());
    let ft = LinkTarget { target: PathBuf::from("f.txt"), is_dir: false };
    if let Err(e) = p.create_symlink(&flink, &ft) {
        if cfg!(windows) {
            return; // no Developer Mode: the OS refuses links, which providers may pass on
        }
        panic!("create_symlink failed: {e}");
    }
    let dt = LinkTarget { target: PathBuf::from("sub"), is_dir: true };
    p.create_symlink(&dlink, &dt).unwrap();
    assert_eq!(p.stat(&flink).unwrap().kind, EntryKind::Symlink);
    assert_eq!(p.read_link(&flink).unwrap(), ft);
    assert_eq!(p.read_link(&dlink).unwrap(), dt);
    assert_eq!(kind_of(p.create_symlink(&flink, &ft)), ErrorKind::AlreadyExists);
    assert!(p.read_link(&file).is_err());
    p.delete(&flink, DeleteMode::Permanent).unwrap();
    assert_eq!(read_all(p, &file), b"target");
}

pub fn check_metadata(p: &dyn Provider, root: &VPath) {
    let d = fresh(p, root, "meta");
    let f = d.join("f.txt").unwrap();
    write_all(p, &f, WriteMode::CreateNew, b"x");
    let when = SystemTime::UNIX_EPOCH + Duration::from_secs(1_000_000_000);
    let mut times = MetadataPatch::default();
    times.modified = Some(when);
    p.set_metadata(&f, &times).unwrap();
    assert_eq!(p.stat(&f).unwrap().modified, Some(when));
    let mut attrs = MetadataPatch::default();
    attrs.attributes = Some(Attributes::READONLY);
    p.set_metadata(&f, &attrs).unwrap();
    let s = p.stat(&f).unwrap();
    assert!(s.attributes.contains(Attributes::READONLY));
    assert_eq!(s.modified, Some(when));
    attrs.attributes = Some(Attributes::empty());
    p.set_metadata(&f, &attrs).unwrap();
    assert!(!p.stat(&f).unwrap().attributes.contains(Attributes::READONLY));
}

    let t = tempfile::tempdir().unwrap();
    let root = t.path().to_path_buf();
    let (src, dst) = (root.join("src"), root.join("dst"));
    std::fs::create_dir(&src).unwrap();
    std::fs::create_dir(&dst).unwrap();

    VPath::local(p.as_ref()).unwrap()

    JobSpec::Transfer(TransferSpec::into_dir(mode, &sources, &v(dest), options).unwrap())

- `run_transfer`(이 태스크 범위): 계획된 파일 항목마다 `attempt` 안에서 `copy_file(.., RenameMode::NoReplace)` → 성공하면 `item_done(true, false)`와 `report.outputs.push(target)`.
- `copy_file` 순서:
  1. `tmp = ctx.temp_for(target)`(`Stage::Write`). 드롭 가드 `TempGuard { provider, path, armed }`가 무장 상태로 사라지면 `delete(&tmp, DeleteMode::Permanent)`(결과 무시). 오류·취소·패닉 모두 이 가드로 지운다.
  2. 링크(`EntryKind::Symlink`이고 `SymlinkMode::CopyLink`)는 Task 10. 파일은 `src.open_read(source)`(`Stage::Read`), `dst.open_write(&tmp, WriteMode::CreateNew)`(`Stage::Write`), `COPY_CHUNK` 버퍼로 `check()?` → `read`(오류는 `Error::io("read", source, e)`, `Stage::Read`) → 0이면 끝 → `write_all`(`Error::io("write", tmp, e)`, `Stage::Write`) → `add_bytes(n, source, 첫 조각이고 entry.size > COPY_CHUNK)` 반복 → `finish()`(`Stage::Write`).
  3. 같은 공급자(`scheme()`이 같음)면 `dst.copy_extras(source, &tmp)`, 그다음 `dst.set_metadata(&tmp, &MetadataPatch::times_of(entry))`. 실패는 `warn(Stage::Metadata)`이고 복사는 계속한다.
  4. `dst.rename(&tmp, target, commit)`(`Stage::Commit`) 뒤 가드 해제.
  5. `dst.set_metadata(target, &MetadataPatch::attributes_of(entry))`, 실패는 `warn(Stage::Metadata)`. 읽기 전용 속성을 커밋 뒤에 거는 이유: Windows에서 읽기 전용 임시 파일은 실패 시 지울 수 없다.
- `FaultyProvider`: 쓰기 스트림은 순번·누적 바이트·결함을 가진 비공개 `FaultyWriter { inner: Option<Box<dyn WriteStream>>, .. }`(`Debug`). `Hold`·`Crash` 상태는 `Mutex` + `Condvar`. `Crash`는 `loop { std::thread::park(); }`로 멈춘다. 잠금은 모두 `lock().unwrap_or_else(PoisonError::into_inner)`로 잡고, `Panic` 결함은 잠금을 놓은 뒤에 패닉한다(풀리는 중의 임시 파일 삭제가 다시 패닉해 프로세스가 중단되지 않게). `rename`의 판정 순서는 (1) 순번을 세고 `FailRename`이면 실패, (2) `CrossDevice`, (3) 위임이다.

- Produces (크레이트 내부 `run_delete(ctx, &DeleteSpec)`, `run_rename(ctx, from, to)`, `run_create(ctx, parent, name, kind)`):
  - 삭제 계획: 경로마다 `stat`(`Stage::Plan`). `Permanent`는 트리를 걸어 파일·링크를 `files`, 폴더를 `dirs`로 세고, `Trash`는 최상위만 센다. 바이트는 세지 않는다(진행률은 항목 수).

  - 휴지통 실행: 최상위 경로마다 `delete(path, Trash)`(`Stage::Delete`). `Deleted::Trashed { location }` → `TrashedItem { original, location }`. 실패(`Unsupported` 등)는 그대로 실패이고 영구 삭제로 바꾸지 않는다(OPS-03). 하나라도 휴지통에 갔으면 `UndoRecord::Trashed { items }`.

  - 이름 바꾸기와 새로 만들기의 계획 합계는 실행 결과와 같은 값 하나(`files: 1` 또는 `dirs: 1`)이고 계획 단계에서 파일을 읽지 않는다.
  - 새로 만들기: 후보는 `parent.join(name)` 다음 `numbered_name(name, 2.., kind == Dir, naming_os)`. `stat`이 `NotFound`인 첫 후보에 `create_dir`/`create_file`(`Stage::Create`). `AlreadyExists`면(경쟁) 다음 후보. 성공하면 `outputs = [path]`, `UndoRecord::Created { path, kind }`.

fn restart(journal: &Path) -> (JobEngine, Receiver<JobEvent>, Vec<IncompleteJob>, usize) {

  - `pub const UNDO_LIMIT: usize = 100;`, `UndoHistory` (`Clone, Debug`): `new(limit: usize)`, `push(&mut self, record)`(사용자 작업: 끝에 더하고 한도를 넘으면 가장 오래된 것을 버리며 다시 실행 목록을 비운다), `pop_undo(&mut self) -> Option<UndoRecord>`, `push_undone(&mut self, reverse)`(되돌리기 결과를 다시 실행 목록에), `pop_redo(&mut self) -> Option<UndoRecord>`, `push_redone(&mut self, reverse)`(다시 실행 결과를 되돌리기 목록에, 다시 실행 목록은 그대로), `undo_list(&self) -> Vec<UndoRecord>`(오래된 것 먼저), `redo_list(&self) -> Vec<UndoRecord>`(다음에 다시 실행할 것이 끝)
  - 되돌리기 실행(`run_undo`, `ctx.interactive = false`: 묻지 않고 충돌은 건너뛰기, 오류는 계속, 사전 검사는 진행). 결과 보고서의 `undo`는 되돌리기를 다시 되돌리는 기록이다(다시 실행이 이것을 실행한다):
    - `Copied { created }`: 항목마다 `stat`. 없으면 `skipped`. 파일인데 크기·수정 시각·identity(둘 다 있을 때) 중 하나라도 기록과 다르면 `Stage::Undo` 실패 `Error::Unsupported(format!("{path} changed after it was copied; left in place"))`. 나머지를 휴지통 삭제(Task 12 규칙, 영구 삭제로 바꾸지 않음) → 역기록 `Trashed`.
    - `Moved { moves, created_dirs, removed_dirs }`: (1) `removed_dirs`를 뒤에서부터(부모 먼저) 없으면 `create_dir`, (2) `moves`를 뒤에서부터 `to → from`의 이동 명세(충돌 `Skip`, 오류 `Continue`, 링크 `CopyLink`)로 Task 11 실행기를 그대로 돌린다, (3) `created_dirs`를 뒤에서부터(자식 먼저) `remove_dir`(비어 있지 않으면 경고). 역기록 `Moved { moves: (2)의 moves, created_dirs: (1)에서 만든 폴더 + (2)의 created_dirs, removed_dirs: (2)의 removed_dirs + (3)에서 지운 폴더 }`.
    - `Renamed { from, to }` → `run_rename(to, from)` → 역기록 `Renamed { from: to, to: from }`.
    - `Created { path, kind }`: 폴더는 `remove_dir`(비어 있지 않으면 `Stage::Undo` 실패, 폴더는 남는다), 파일은 크기 0일 때만 `delete(Permanent)`(아니면 `Stage::Undo` 실패 `"{path} is not empty; left in place"`) → 역기록 `Removed { path, kind }`. `Removed`는 그 경로에 그대로 만든다(번호 없음) → `Created`.
    - `Trashed { items }`: `location`이 있는 항목마다 `restore_trashed(location, original)`(`Stage::Undo`), 없으면 `Stage::Undo` 실패 `"trash location of {original} is unknown"` → 역기록 `Restored { items: 복원한 것 }`. `Restored { items }` → `original`들을 휴지통 삭제 → `Trashed`.
  - 엔진: `pub fn undo(&self) -> Option<JobId>`(되돌리기 목록에서 꺼내 `Undo` 작업으로 제출), `pub fn redo(&self) -> Option<JobId>`, `pub fn undo_history(&self) -> Vec<UndoRecord>`, `pub fn redo_history(&self) -> Vec<UndoRecord>`. 작업이 끝날 때 `Finished` 이벤트를 보내기 전에 기록을 갱신한다: 사용자 작업의 `undo`가 있으면 `push`, 되돌리기 작업이면 `push_undone`, 다시 실행 작업이면 `push_redone`. 기록이 없는 작업(영구 삭제 등)은 목록을 건드리지 않는다.
